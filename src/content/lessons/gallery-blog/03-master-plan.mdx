The mockup is done. We know what the gallery looks like. Now — before any real code — we meet the document that runs this entire build.

It's called **the master plan**. It's not a tutorial; it's a blueprint, written for exactly one situation: someone (or something) starting this app from an empty folder. Every remaining lesson in this project maps to a phase inside it.

You're the builder. opencode is your assistant. The plan keeps you both honest.

## One app, not a pile of apps

The stack from lesson 1 — Express, EJS, Neon, R2 — is exactly this plan's stack. But there's a detail a stack list can't show you: it's **one Express app that does everything.**

It renders its own pages (EJS), handles its own forms (plain HTML), talks to Neon for data, and to R2 for photo files. There is no separate client project, no build step for the browser, no CORS, no API contract to keep in sync.

<Callout variant="haa" title="Haa!">
"Boring" is not a dirty word here. Every piece the plan deliberately leaves out — a front-end framework, a CSS framework, a bundler, a session table — is one less thing that can break at 2am. Fewer moving parts is not a compromise. It's the feature.
</Callout>

The plan calls the app's own features — photo folders, likes, comments — **extensions**. They plug into fixed seams; they never rewrite the core. That's why we can build the whole thing in one course and still have room to grow it after.

<Callout variant="warn" title="No skipping">
Every phase ends with a verification step — the plan calls it <strong>Verify:</strong>. Pass it before touching the next phase. Skipping ahead feels fast; it's actually the slowest way to build, because now you're debugging three unknown layers at once.
</Callout>

## What the plan is strict about

The plan has a section called **hard invariants** — rules it will not bend. You'll meet them one by one, but here's the flavor:

- **Auth is one owner.** Your email and password live in environment variables, never in the database. There's no users table, no signup, no password reset. Nothing to attack because nothing is stored.
- **The database changes slowly, on purpose.** Migrations are generated, then **read by a human** (you), then applied by hand. Deploys never run them.
- **Images never touch our server.** The browser uploads straight to R2 with a short-lived signed URL. The database stores the key, not the file.

Don't memorize these yet. Just notice the pattern: every invariant is a decision that trades a little convenience for a lot of safety.

## The facts you'll be asked for

Some phases pause and need real values from you. Nothing secret ever goes into the plan document itself — secrets live in a `.env` file that never gets committed:

| Fact | Where it ends up |
| --- | --- |
| App name + one-line purpose | `APP_NAME`, page titles |
| Production domain | `PUBLIC_BASE_URL`, R2's CORS list |
| Your login email + a 12+ character password | `ADMIN_EMAIL`, `ADMIN_PASSWORD` |
| Neon connection string (pooled host) + a second branch for tests | `DATABASE_URL`, `TEST_DATABASE_URL` |
| Cloudflare account id, bucket name, R2 API token | `R2_*` |
| Public or private images? | `R2_PUBLIC_BASE_URL` |

You don't need all of these today. You'll need each one exactly when its phase arrives — and the lesson will tell you.
