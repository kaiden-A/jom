A photo is big. A database row is small. Putting photos *in* the database is the classic beginner mistake — rows get obese, queries crawl, backups balloon.

The master plan keeps them apart: **the file lives in R2, the row lives in Neon, and the row holds only a key like `images/2026/<uuid>.jpg`.** Everything interesting in this phase is about how the file gets to R2, because the answer is not what most tutorials do.

## Why a presigned URL is the trick

The naive design: the browser POSTs the file to our server; our server PUTs it to R2; the browser gets a URL back. The plan refuses:

- **Our server never handles the bytes** — no 10MB request bodies through Express, no memory spikes, no timeouts on slow connections.
- **The browser never gets the credentials.** Instead, `POST /uploads/sign` hands out a *ticket*: a URL that is signed, scoped to one key, one method (PUT), one content type, and expires in 5 minutes. A leaked ticket is nearly worthless: it can only overwrite one specific key, that one time.
- **The upload request carries no cookies** — it goes to Cloudflare, not us. Session cookies stay home.

<Callout variant="haa" title="Haa!">
Notice how this mirrors the auth design from phase 3. There, credentials stayed on the server and the browser got a limited, expiring *cookie*. Here, R2 credentials stay on the server and the browser gets a limited, expiring *URL*. Same instinct, different layer: never give a client the keys — give it a ticket.
</Callout>

## The code, both halves

The sign endpoint is the app's one JSON endpoint:

```ts
// src/routes/uploads.ts
router.use(requireAuth(settings, "json"));   // not a page — a 401 here, not a redirect

router.post("/sign", async (req, res) => {
  if (!storage.configured) throw new HttpError(503, "Image storage is not configured.");
  const { contentType, size } = SignIn.parse(req.body);
  const ext = ALLOWED_TYPES[contentType];
  if (!ext) throw new HttpError(400, "Use a JPEG, PNG, WebP, GIF or AVIF image.");
  if (size > settings.IMAGE_MAX_BYTES) throw new HttpError(400, "That image is too large.");
  const key = newImageKey(ext);                                  // images/<yyyy>/<uuid>.<ext>
  const uploadUrl = await storage.createUploadUrl(key, contentType);
  res.status(201).json({ key, uploadUrl, expiresIn: 300 });
});
```

And the rule that must hold before a key is ever written to the database:

```ts
// src/services/image_services.ts
export const ALLOWED_TYPES: Record<string, string> = {
  "image/jpeg": "jpg", "image/png": "png", "image/webp": "webp",
  "image/gif": "gif", "image/avif": "avif",
}; // raster only: never SVG

export async function assertUploadedImage(storage: Storage, key: string, maxBytes: number) {
  if (!KEY_PATTERN.test(key)) throw new HttpError(400, "That image isn't valid. Choose it again.");
  const object = await storage.head(key);
  if (!object) throw new HttpError(400, "The image didn't finish uploading. Try again.");
  if (object.size > maxBytes || !(object.contentType in ALLOWED_TYPES)) {
    await storage.remove(key).catch(() => undefined);
    throw new HttpError(400, "That file isn't an allowed image.");
  }
}
```

Two layers of trust control here. **SVG is banned by name** — an SVG is a little XML document that can carry scripts, and serving one from your domain is stored XSS with extra steps. Raster formats only. And the server doesn't take the client's word at sign-time: before trusting a key, it re-checks with `HeadObject` — does the object exist, is it the right size, is it really an allowed type. A key from a form is accepted only if it matches the minted pattern **and** the object verifies.

<Callout variant="warn" title="The two classic R2 footguns">
<strong>1. Content-Type must match exactly.</strong> The PUT must send *exactly* the `file.type` that was signed — change it and R2 answers `403 SignatureDoesNotMatch`. <strong>2. Newer AWS SDKs add CRC checksum parameters</strong> that R2's presigned URLs reject. The plan initializes the client with `requestChecksumCalculation: "WHEN_REQUIRED"` — one line that saves an afternoon.
</Callout>

## Reading images back

Views never see keys. They get `imageUrl`, built fresh on every render:

```ts
async readUrl(key: string) {
  if (this.s.R2_PUBLIC_BASE_URL) return `${this.s.R2_PUBLIC_BASE_URL.replace(/\/$/, "")}/${key}`;
  const cmd = new GetObjectCommand({ Bucket: this.s.R2_BUCKET, Key: key });
  return getSignedUrl(this.client, cmd, { expiresIn: 3600 });   // signed GET, one hour
}
```

Public base set → stable unsigned URL. Not set → a signed GET that lives for an hour, freshly signed on each page render. (And now the CSP from phase 4 makes sense: `connect-src` and `img-src` allow the R2 host because the browser is a first-class citizen in this design.)

<Callout variant="tip" title="The hour-long mystery">
Someone leaves a tab open all evening, comes back, and every image is 403. Nothing broke — the signed GET URLs expired. Reload fixes it; `R2_PUBLIC_BASE_URL` removes the class of problem for public images.
</Callout>

## DB first, R2 second

Deleting a photo deletes two things in a fixed order — and the order is the lesson:

```ts
const [row] = await db.delete(photos).where(eq(photos.id, id)).returning();
if (!row) throw new HttpError(404, "Not found.");
if (row.imageKey) {
  await storage.remove(row.imageKey).catch((e) => console.warn("R2 delete failed:", row.imageKey, e));
}
```

Row first, object second. If the object delete fails: log it, and **never fail the user's request** — the database already told the truth, and a dangling object is cheap. Leftovers get collected by the optional `scripts/sweep-orphans.ts`: it lists `images/` objects older than 24 hours that no row references, dry-run by default, deletes with `--apply`. Database is the source of truth; the bucket is allowed to be eventually-clean.
