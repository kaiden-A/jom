## House rules

The plan calls these **hard invariants**, and the plan means it: if a requirement seems to conflict with one, you stop and ask — you never break the invariant. Here's the whole set, arranged the way you'll actually meet them:

<div class="not-prose my-8 grid gap-4 sm:grid-cols-2">
  <div class="clay p-5">
    <p class="font-display text-base font-semibold">Auth & sessions</p>
    <ul class="text-ink-soft mt-3 space-y-2 text-sm leading-relaxed font-bold">
      <li>Credentials live only in env vars — never stored, logged, rendered, committed.</li>
      <li>A cookie counts only if the signature verifies, it's unexpired, and <code class="font-mono text-xs">sub</code> still matches ADMIN_EMAIL.</li>
      <li>Every non-GET with an Origin must match PUBLIC_BASE_URL. Every <code class="font-mono text-xs">next</code> goes through <code class="font-mono text-xs">localPath()</code>.</li>
    </ul>
  </div>
  <div class="clay p-5">
    <p class="font-display text-base font-semibold">Database</p>
    <ul class="text-ink-soft mt-3 space-y-2 text-sm leading-relaxed font-bold">
      <li>Pooler-safe always: schema-qualified SQL, no session state, no named statements.</li>
      <li>snake_case in the database, camelCase in code — the mapping lives in one layer.</li>
      <li>Migrations: generated, <span class="text-ink">read by hand</span>, applied by hand. Deploys never migrate.</li>
    </ul>
  </div>
  <div class="clay p-5">
    <p class="font-display text-base font-semibold">Pages & HTTP</p>
    <ul class="text-ink-soft mt-3 space-y-2 text-sm leading-relaxed font-bold">
      <li>Post/redirect/get. A successful POST never renders — it 303s.</li>
      <li><code class="font-mono text-xs">&lt;%= %&gt;</code> for data; <code class="font-mono text-xs">&lt;%- %&gt;</code> only for includes. No inline script or style, ever.</li>
      <li>Mutations are POST forms. A GET never changes anything.</li>
    </ul>
  </div>
  <div class="clay p-5">
    <p class="font-display text-base font-semibold">Images & R2</p>
    <ul class="text-ink-soft mt-3 space-y-2 text-sm leading-relaxed font-bold">
      <li>The browser gets tickets, never credentials: one key, one method, 5 minutes.</li>
      <li>The database stores keys; server-minted, HeadObject-verified, raster-only.</li>
      <li>DB first, R2 second. A failed object delete never fails a user's request.</li>
    </ul>
  </div>
</div>

<Callout variant="note" title="Why “invariant” and not “guideline”">
Because these are the rules that, when followed, make entire categories of bugs *impossible* rather than *fixed*. A pooler can't break schema-qualified SQL. A stolen cookie can't be edited. A refresh can't double-write. That's the difference between patching and designing.
</Callout>

## Now make it yours

The plan doesn't end at "done" — it ends with the **extension playbook**: the seams where new features plug in without touching the core. You've used every one of them already; here's the map for the gallery's missing features:

- **Folders** — a `folder_id` on `photos`, a `folders` resource through the exact six-file pattern from lesson 8, and a `?folder=` filter on the list route. Two files change; nothing else does.
- **Likes** — a `likes` table (photo id + timestamp), a `POST /photos/:id/like` route, and the count folded into `photoView`. Your first write that isn't admin-only — so it's also your first rate-limit conversation.
- **Comments** — the same shape, with the body validated by zod and rendered with `<%= %>`. (Guess why the escaping rule matters most here.)

And beyond the gallery, the playbook covers the patterns for external APIs (wrap in a small class with a `configured` flag and a fake for tests), email (`send()` that logs in dev, fakes in tests, always best-effort), and scheduled work (a CLI script under `src/scripts/`, idempotent, dry-run by default — `sweep-orphans.ts` is the model).

<Callout variant="haa" title="Haa!">
Look at what you actually built: not just a photo site, but a *position* — one owner, three seams, eight verified phases, and a documented answer for every question a new feature can ask. That's why the plan spent four pages on invariants and one on code structure. The code was never the hard part.
</Callout>
