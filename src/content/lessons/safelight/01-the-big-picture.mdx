A photograph is the easiest thing in the world to copy. So what is a customer actually buying?

Not the pixels. They can screenshot the preview. Not the file, exactly — a file can be duplicated forever. What they are buying is **a clean original and the right to use it**, delivered after the shop has verified the payment.

That sounds simple. It is not. Most tutorials stop at "click buy" and assume the file appears. This project starts where those tutorials stop: **the last mile**. The payment is manual, the confirmation is human, and the original is kept in a private vault until the shop says yes.

That is the whole project. Let's meet it properly.

## Why "Safelight"?

In a darkroom, a safelight lets you see what you are doing without ruining the print. It is a small, controlled light in a room that has to stay dark.

That is exactly the relationship between the preview and the original:

- The **preview** is the safelight. It is bright enough to sell the photograph, but it is watermarked and downscaled so it cannot replace the original.
- The **original** stays in the dark: a private R2 bucket, no permanent public URL, no shortcut.

<Callout variant="note" title="The name is part of the design">
Safelight is the working name for this project. The visual language follows from it: warm paper, ink, a single darkroom-red accent, serif titles, and monospaced order numbers. It should feel like a gallery ledger, not a generic e-commerce template.
</Callout>

## The two doors

Here is the mental model I want you to keep for the rest of the project. Everything else is implementation detail.

<TrustBoundaries client:visible />

The important part is not the bucket. It is the **asymmetry**:

- The preview is allowed to be public. It is marketing.
- The original is never public. It is inventory.
- The email link is not a storage URL. It is a **ticket** to the app, which can be checked, revoked, and reissued.

If you remember one sentence from this lesson, make it this one:

> **The email link is a ticket, not the file.**

## What is actually hard here

Uploading a photo and listing it is the easy part. The gallery project already taught that. Safelight adds four problems that are mostly about **state**, not UI:

1. **The price must be frozen.** A photograph can cost RM 180 today and RM 240 next week. An order created today must still be RM 180 forever.
2. **Payment confirmation must happen once.** A double-click, a retry, or two admin tabs must not send two emails or create two paid events.
3. **Email can fail without un-paying the order.** The order is paid because the money arrived. The email is a separate side effect with its own status and retry button.
4. **A download must be an entitlement, not a URL.** The original file needs a token that can expire, be revoked, and be reissued without uploading the file again.

That is why the database is not just a list of photos. It is the source of truth for **who is allowed to receive which file, and why**.

## The state machine

The order is the heart of the system. It only moves in a few directions, and every move has a guard.

```text
pending_payment ──admin verifies──▶ paid ──admin refunds──▶ refunded
       │
       └──admin cancels──▶ cancelled
```

Two rules matter more than the diagram:

- **Only `pending_payment` can become `paid`.** Not `cancelled`, not `paid` again, not "probably paid".
- **Email status is separate from payment status.** A paid order with a failed email is still paid. The customer is entitled to the file; the email is just how they find out.

We will build both as explicit database constraints and conditional updates, not as `if` statements scattered through the UI.

## What we are not building

<Callout variant="warn" title="Scope is a feature">
No customer accounts. No cart. No subscriptions. No Stripe checkout. No reviews. No search. No multi-currency. Each one is a real product decision, and each one would make the first version harder to finish and easier to get wrong.

The manual WhatsApp workflow is not a limitation we are apologising for. It is the workflow many small shops actually use. The project is about making that workflow **safe**, not replacing it with a payment gateway.
</Callout>

This matters because the interesting engineering is not in the checkout UI. It is in the moment after the customer says "I've paid" and before the original leaves the vault.

## The five promises

These are the invariants the rest of the project will protect. We will turn them into database constraints, conditional updates, and tests.

1. **The price comes from the catalog.** The browser never sends an amount.
2. **Only the admin can confirm a payment.** A customer's claim is recorded, not trusted.
3. **No email goes out before an order is paid.** Payment and email are separate states.
4. **The original is never public.** Only a signed, short-lived URL can read it.
5. **Unpublishing a photograph does not revoke a paid download.** The gallery hides it; the entitlement survives.
