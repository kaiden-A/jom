Everything so far has lived in the browser. The calculator's food list is local. But real apps get data from somewhere else: a server, a database, an API.

An **API** is just a set of URLs that return data. You send a request; it sends back a response, usually JSON.

## Request and response

```
GET https://example.com/v1/foods?q=chicken
```

- `GET` is the method. You're asking to read something.
- The URL is the **endpoint**.
- `?q=chicken` is a **query parameter** — extra information for the server.
- The response usually looks like JSON:

```json
{
  "foods": [
    { "id": "chicken-breast", "name": "Chicken breast", "calories": 165 }
  ]
}
```

JSON looks like a JavaScript object, but it's text. `response.json()` parses it into real objects.

## Synchronous vs asynchronous

Some code finishes immediately:

```js
const total = 2 + 2;
```

Network requests don't. The data might take 50ms or 5 seconds. JavaScript doesn't freeze the whole page waiting; it gives you a **Promise** — a placeholder for a value that will arrive later.

`async` and `await` let you write asynchronous code that reads like normal code:

```js
async function loadFoods() {
  const response = await fetch("/v1/foods");
  const data = await response.json();
  console.log(data);
}
```

- `async` marks the function as asynchronous.
- `await` pauses that function until the promise settles.
- The rest of the page keeps working while it waits.

## fetch, step by step

```js
async function loadFoods() {
  try {
    const response = await fetch("https://example.com/v1/foods");

    if (!response.ok) {
      throw new Error("Request failed: " + response.status);
    }

    const data = await response.json();
    console.log(data.foods);
  } catch (error) {
    console.error("Something went wrong:", error);
  }
}
```

<Callout variant="warn" title="fetch does not throw on 404">
A 404 or 500 is still a completed HTTP response, so `fetch` resolves normally. You have to check `response.ok` (true for 200–299) and handle the bad status yourself. Only network failures reject the promise.
</Callout>

Status codes worth knowing:

- `200` — OK.
- `400` — bad request (your input is wrong).
- `404` — not found.
- `500` — server error.

## Loading and error states

A good UI tells the user what's happening:

```js
button.disabled = true;
status.textContent = "Loading...";

try {
  // fetch and render
  status.textContent = "Loaded 4 foods.";
} catch (error) {
  status.textContent = "Could not load foods. Try again.";
} finally {
  button.disabled = false;
}
```

The `finally` block runs whether it worked or not. Re-enable the button there, not inside `try`, or it stays disabled after an error.

<Callout variant="tip" title="What is CORS?">
Browsers block JavaScript from reading responses from another origin unless the server explicitly allows it. That's CORS. A public API sends `Access-Control-Allow-Origin: *`; your own API will allow your site. If you see a CORS error in the console, the request may have succeeded — the browser just refuses to let your code read the response.
</Callout>

## The mistakes everyone makes

- **Forgetting `await`.** You get a Promise instead of the data.
- **Not checking `response.ok`.** A 404 is treated as success.
- **Calling `.json()` twice.** The body can only be read once.
- **Assuming the data is an array.** Many APIs wrap it: `data.recipes`, `data.foods`, `data.items`.
- **No loading state.** The user clicks and nothing happens for two seconds.
- **No error handling.** One failed request leaves the UI stuck.
- **Blocking the page.** Don't use synchronous requests; they don't exist in modern fetch anyway.
- **Storing the response in a global you never use.** Render it.
